1) ليه محتاجين Constraints؟ (سلايد 16 و 17)

جوه Box<T> الـ compiler مش عارف حاجة عن T غير إنها object. فمينفعش تنادي item.Print(). والـ compiler لازم يتأكد وقت الـ compile، مش وقت التشغيل (عكس dynamic أو Reflection). الحل: constraint هو "وعد" بإن T لها شكل معين، والـ compiler يتحقق منه عند كل استخدام.

public class Printer<T> where T : IPrintable
{
    public void Print(T item) => item.Print();   // ينفع لأن T مضمون إنها IPrintable
}
// new Printer<string>();    // خطأ compile: string مش IPrintable

الـ constraint بيعمل 3 حاجات: يفتح لك أعضاء النوع، يمنع الاستخدام الغلط، ويساعد الـ JIT يولّد كود أسرع.

3) الدمج والترتيب (سلايد 23 و 24)

where T : BaseEntity, IAuditable, new()      // ترتيب إجباري
  1. أول واحد: class أو struct أو BaseClass أو notnull أو unmanaged (واحد بس منهم).
  2. بعده: أي عدد من الـ interfaces.
  3. آخر واحد: new().

4) مشاكل Constraints الحقيقية

1) لازم تكرر الـ constraints في الـ derived:

class Base<T> where T : class { }
class Derived<T> : Base<T> { }                 // CS0452: T لازم تكون reference type
class Derived2<T> : Base<T> where T : class { }   // الصح (أو أقوى)

الـ compiler مش بيورّث القيود تلقائياً لأنها جزء من توقيع النوع، فلازم تذكرها صراحة (ومسموح تزيد عليها).

2) new() بتتعارض مع الـ DI: الـ new T() بتنشئ object من غير ما تحقن dependencies، فلو الـ class محتاجة ILogger مش هتشتغل. للخدمات استخدم IServiceProvider أو factory delegate (Func<T>). والـ new() مناسبة للـ DTOs و entities البسيطة.

3) القيد بالـ interface بيمنع Boxing، والـ parameter بـ interface بيعمله:

static int Cmp1<T>(T a, T b) where T : IComparable<T> => a.CompareTo(b);   // بدون boxing للـ struct
static int Cmp2(IComparable<int> a, int b)             => a.CompareTo(b);   // الـ int بيتحول لـ interface (boxing)

الـ JIT بيعمل "constrained call" في الأولى ويولّد كود مخصص لكل struct فمفيش allocation.

4) constraints بـ class محددة بتربطك: where T : BaseEntity بتخليك ما تقدرش تستخدم الكود مع أي نوع مش وارث. فضّل interface (where T : IEntity) لتبقى مرن، وارجع للـ base class بس لو محتاج كود مشترك فعلاً.

5) sizeof(T) مع struct: مش بتتكمبل (مش مضمون إن النوع unmanaged). استخدم where T : unmanaged مع unsafe، أو الأسهل Unsafe.SizeOf<T>().

الحديث: من C# 11 تقدر تكتب where T : INumber<T> وتستخدم + و * مباشرة على T (Generic Math)، وده كان مستحيل قبلها بدون تكرار الكود. وفي C# 13 اتضاف allows ref struct كـ anti-constraint عشان تقبل Span<T> كـ type argument.

5) Variance: in و out (سلايد 25 إلى 29)

السؤال

لو Dog : Animal، هل X<Dog> تنفع مكان X<Animal>؟ الإجابة بتعتمد على اتجاه استخدام T جوه X.

ليه الاتجاه كده؟ (قاعدة بسيطة)

  • out (منتج): الـ IEnumerable<Dog> بيطلع كلاب فقط. كل كلب هو Animal، فلو حد طلب "مصدر حيوانات" وأنا مديه "مصدر كلاب" مفيش مشكلة.
  • in (مستهلك): Action<Animal> قادر يتعامل مع أي حيوان، فبالتأكيد قادر يتعامل مع كلب. فلو حد طلب "معالج كلاب" وأنا مديه "معالج حيوانات" مفيش مشكلة.
  • invariant (الاتنين): List<T> بتقرأ وبتكتب. لو قبلت List<Dog> كـ List<Animal> حد يقدر يضيف Cat لقايمة كلاب.
// سلايد 27 و 28
public interface IProducer<out T> { T Get(); }
class DogProducer : IProducer<Dog> { public Dog Get() => new Dog { Name = "Buddy" }; }
IProducer<Animal> animals = new DogProducer();        // covariance
Console.WriteLine(animals.Get().Name);                  // Buddy

// سلايد 25 و 26
public interface IProcessor<in T> { void Process(T item); }
class AnimalProcessor : IProcessor<Animal> { public void Process(Animal a) => Console.WriteLine($"Processing {a.Name}"); }
IProcessor<Dog> dogs = new AnimalProcessor();         // contravariance
dogs.Process(new Dog { Name = "Rex" });

القواعد

  • out T مسموح تظهر في return فقط. لو حطيتها كـ parameter: خطأ CS1961.
  • in T مسموح تظهر في parameters فقط.
  • تنطبق على interfaces و delegates فقط (مش classes ولا structs).
  • تنطبق على reference types فقط: IEnumerable<int> مش بتتحول لـ IEnumerable<object> لأن الـ int يحتاج boxing (تمثيل مختلف في الذاكرة).
  • الأمثلة في الـ BCL: IEnumerable<out T>، IReadOnlyList<out T>، Func<in T, out TResult>، Action<in T>، IComparer<in T>، IEqualityComparer<in T>. لكن List<T> و IList<T> invariant.

تطبيق حقيقي

void Feed(IEnumerable<Animal> animals) { }        // خذها بـ IEnumerable مش List
Feed(new List<Dog>());                           // يشتغل بفضل covariance
// void Feed(List<Animal> animals)  ← كان رفض List<Dog>

class ByName : IComparer<Animal>
{ public int Compare(Animal? a, Animal? b) => string.Compare(a?.Name, b?.Name); }
var dogsList = new List<Dog>();
dogsList.Sort(new ByName());                        // comparer للحيوانات بيرتّب كلاب (contravariance)

الأصل التاريخي لباگ: المصفوفات covariant من أول نسخة (قرار قديم غير آمن): object[] a = new string[1]; a[0] = 5; بتتكمبل وبترمي ArrayTypeMismatchException وقت التشغيل، وكل كتابة في array بتعمل فحص نوع إضافي. الـ generics اتصممت بحيث تتجنب ده.

إمتى تحتاج تكتب variant interface بنفسك؟ لما تعمل handlers و validators و producers عامة (IHandler<in TMessage>، IValidator<in T>، IReader<out T>) وعايز تسجل handler واحد عام لأنواع أخص.

6) Generic Inheritance (سلايد 30 إلى 33)

الأشكال التلاتة

class A<T> { public T Value { get; set; } = default!; }

class B : A<int> { }                  // 1) closed: النوع ثابت
class C<T> : A<T> { }                // 2) open pass-through: النوع بيتمرر (سلايد 31)
class D<T> : A<List<T>> { }          // 3) النوع مشتق منه

مشاكل حقيقية

1) A<int> و A<string> مالهمش أب مشترك: مينفعش تحطهم في List<A<?>> ومينفعش void F(A<object> a) تقبل A<string>. الحل: interface أو base class غير generic (IEntity) فوقهم.

2) كل closed base ليه static خاص: B و C<int> يشاركوا A<int>، لكن C<string> لأ.

3) عمق الـ hierarchy: 3 مستويات generic (Entity<TId> ثم AuditableEntity<TId> ثم SoftDeletable<TId>) بتصعّب القراءة وأخطاء الـ compiler. فضّل composition أو interfaces صغيرة (IAuditable و ISoftDeletable) على سلسلة وراثة طويلة.

نمط متقدم: Self-referencing constraint (Fluent Builder)

public abstract class Builder<TSelf> where TSelf : Builder<TSelf>
{
    protected string _name = "";
    public TSelf Name(string n) { _name = n; return (TSelf)this; }   // يرجع النوع الأخص
}
public class PizzaBuilder : Builder<PizzaBuilder>
{
    private bool _cheese;
    public PizzaBuilder Cheese() { _cheese = true; return this; }
    public string Build() => $"{_name} cheese={_cheese}";
}
Console.WriteLine(new PizzaBuilder().Name("Margherita").Cheese().Build());   // Name بترجع PizzaBuilder فنقدر نكمل Cheese()

من غير TSelf كانت Name() هترجع Builder الأساسي وتضيع عليك Cheese() في السلسلة. نفس الفكرة وراء IComparable<T> و INumber<T>.
